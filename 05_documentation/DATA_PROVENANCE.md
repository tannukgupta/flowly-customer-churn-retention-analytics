# Flowly Dataset — Data Provenance & Reproducibility

## What is this data?

This portfolio project uses **simulated business data** for a fictional SaaS company named **Flowly**.

No real customer records or proprietary company data are being claimed or represented.

## How was the data created?

The dataset was generated programmatically with Python.

The generation process was:

1. Design a relational business model around customers, subscriptions, transactions, usage activity, support, marketing and churn.
2. Define business distributions for plans, countries, acquisition channels, billing cycles, payment methods, etc.
3. Generate 10,000 customer records.
4. Generate related records using the `customer_id` key.
5. Apply documented simulation rules so behavioral variables are not independent random noise.
6. Generate churn outcomes from a probability model using those simulated behavioral attributes.
7. Intentionally inject a small number of missing values and duplicate-looking activity records so a realistic data-cleaning stage can be demonstrated.
8. Export each relational entity to its own CSV.

## Reproducibility

The generator uses the fixed random seed:

**20260918**

Running:

```bash
python generate_flowly_data.py
```

recreates the same logical dataset from the same code and seed.

## Why create simulated data?

Customer-level churn history, activity, billing and support data are commonly confidential. Creating a transparent simulated environment lets the project demonstrate the full analytics workflow without implying access to private customer information.

## Important analytical limitation

The churn patterns are intentionally generated by the simulation rules. Therefore:

- observed relationships are useful for analytical practice;
- they are **not** evidence of causal relationships in a real business;
- project conclusions should be worded as associations, patterns or hypotheses.

## Suggested interview wording

> “I created a simulated SaaS business environment in Python because real customer churn data is generally confidential. I first designed a relational schema, then generated linked customer, subscription, transaction, activity, support and marketing tables using a fixed random seed and documented business rules. I also introduced controlled data-quality issues so I could demonstrate the cleaning and validation stage. I then used SQL, Python and Power BI for the analysis and reporting.”
